# 资料更新后的原问题复核与两版回答对照

2026-11-11。基线 `4f699bb01fa051a4ba6a6ef9d3b22998dadc4292`，分支 `codex/knowledge-version-compare`。

## 缺口与交付

核对既有 KnowledgeAnswer、源版本比较、逐份问答和研究笔记后，确认已有能力分别覆盖资料原文对比、保留旧问答、同题逐份回答和结果汇编，但没有把一条旧版回答带到新版复核并同时保留两份答案的流程。手动改变范围重新发送会替换当前页面回答，也容易把后来编辑的问题误当成原问题。

本次交付一个完整模块：读取限定单份资料的成功问答 → 核对同一资料有更新的可用版本 → 确认原问题、原关键词和版本变化 → 再次核对 → 提交独立新版问答 → 保留原回答并排阅读 → 分别打开精确引用。准备和取消不调用模型；当前问题、关键词草稿与原问答均不被覆盖。新回答不把旧回答当作输入。

两份回答分别沿原有问答历史持久化合同保存，后续可用已有历史入口、记忆草稿及研究笔记流程处理。本次不增加持久化的“对照关系”：并排面板只保留在当前连接，切页保留、重连清空。没有自动修订既存记忆、全库回答转单份回答、自动更换关键词或生成事实差异结论。

## 实现与取舍

- 新 `KnowledgeAnswerRecheck` 使用既有受控列表定位原问答，再从 ACTIVE 资料列表重新取得文档资格和详情。必须为同一 ID、列表与详情创建时间一致、READY、存在原源版本、当前可用版本严格更新。缺失／归档／处理中／没有新版／全库原回答均停止，不扩大范围。
- 确认前展示固定的两版及原问题；提交前重新读取并比较完整原问答与资料元数据。变化要求重新准备，离页／服务不可用使未提交确认失效，读取整体期限 30 秒。确认与实际提交之间不是数据库事务快照；Runtime 仍负责最后的精确版本准入，拒绝不会自动更换版本。
- 复用 `knowledge.answerSubmit/Get/Cancel`，没有 Java、C#、Bridge 合同、schema 或新依赖。任务受理后保留确切编号；额外校验引用必须属于新版本。异常回执保留核对入口，不采用越界回答；如果提交回执复用了原问答 ID，不把原任务当成新版去取消或查询。
- 原问答界面与研究笔记在准备／执行／未知结果期间互斥；未知提交没有新任务编号时持续阻止再次发送，不从相似历史猜测。已知编号只核对该任务，取消只发一次，离页暂停轮询但保留同连接在途回执，连接变化忽略迟到回执。
- 两栏独立使用既有安全 Markdown 阅读器，窄屏布局按可用宽度排列。各引用仍使用自己的文档 ID／版本／偏移。文字相同／不同仅作字面提示，明确模型和检索差异也可能改变答案，不宣称差异就是事实更新。

取舍参考 [LibreChat 的独立分叉交互](https://www.librechat.ai/docs/features/fork)：保留原结果，再产生独立分支。其 [LICENSE 为 MIT](https://github.com/LibreChat-AI/LibreChat/blob/main/LICENSE)，[Releases](https://github.com/LibreChat-AI/LibreChat/releases) 当前有 v0.8.9-rc1 等维护记录（标记为预发布）。这里只参考保留原结果的交互原则；完整聊天树及其服务不适配本项目已有的独立问答／不可变源版本合同，因此没有复制代码、下载依赖或引入第二套持久层。未把上游预发布当成本项目验收依据。
