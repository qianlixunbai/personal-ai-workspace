# Knowledge 上传回执与后台任务交接

2026-11-12，基于 `f597c2b6e3cf317885fb39c501ca80ea3ad04f62`。

继续审阅导入取消／失败后的恢复链路时，确认了另一个接收结果不一致：原 `KnowledgeIngestion.receive()` 先提交后台任务，再查询 `store.job(request)` 构造上传响应。后台可能已经失败或完成并清理、释放所有权；同一资料的新重试替换 `last_job` 后，再一次准入会正常回收旧任务。原上传调用此时查不到自己的任务，将返回 `KNOWLEDGE_NOT_FOUND`，尽管文件已经接收并处理。这不是上一轮“仍有文件待清理却丢失恢复身份”的重复修复，而是清理已结束、上传响应尚未构造的交接缺口。

现在在上传调用仍持有任务时取得不可变 `Job` 快照，再提交后台任务；只在提交成功后返回回执。队列拒绝仍走原失败／清理分支，不返回虚假接收成功。生产调用和定向回归共用 `enqueueWithReceipt`，没有新增后台线程、重试或持久化状态。

协议字段、NativeGate、归属、队列容量、任务回收规则和文件清理范围不变。新上传通常返回提交前的 PENDING 快照，若接收期间已经取消则保留取消快照；后续状态仍通过原查询获得。`knowledge.ts` 接受这些状态，单文件页面读取资料详情，批量导入对 PENDING／PARSING 继续查询。因此不要求同步完成，也不再依赖“后台还没来得及回收记录”的时序。此修改不承诺被后续导入取代或已删除资料的旧任务永久可查。
