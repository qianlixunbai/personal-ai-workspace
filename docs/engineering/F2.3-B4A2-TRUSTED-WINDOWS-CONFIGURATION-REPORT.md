## 3. 可信配置存储机制

新增 `persistence/TrustedDatabaseConfiguration`，唯一配置位置为 **Gate 实际准入的 Profile 根 / data / database.dpapi**；调用方不能指定路径。
`load()` 与内部供给接口 `create(byte[])` 都先调用原 `WindowsNativeGate.profileRoot()`，拒绝后不会继续访问文件或 DPAPI。
`create` 尚无 CLI、HTTP 或 WebView 调用入口，不构成开放的产品配置写入功能。

整个 UTF-8 配置用 Windows DPAPI CurrentUser 保护，使用现有 JNA 的 Crypt32 实现，flags 为 `CRYPTPROTECT_UI_FORBIDDEN`，不设置 `CRYPTPROTECT_LOCAL_MACHINE`，没有固定加密密钥或新依赖。
依据 [Microsoft CryptProtectData 文档](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)，这属于账户本地保护；产品跨设备恢复必须重新配置凭据，独立完成 Finance 身份确认，不能把 DPAPI 密文复制当成恢复凭据的机制。
现有逻辑备份和统一 PostgreSQL 备份按业务表及列出的 Knowledge revision 文件导出，本轮没有把该本机配置加入备份格式。

只接受 format 整数 `1` 和严格字段集合 `format/backend/host/port/database/username/password`；拒绝重复键、未知键、额外 JSON、BOM、非法 UTF-8 和超出大小预算的内容。
backend 必须为 `postgresql`，host 固定 `127.0.0.1`，port 为 `1..65535`；数据库与角色为受限小写标识符，拒绝系统数据库、`postgres` 应用角色及 `pg_` 角色。
角色实际权限和现有 schema 规则继续由原只读检查及 Store 验证；没有创建数据库、角色或 schema。

读取前后验证 owner / protected private ACL、全部祖先无 symlink/reparse、Win32 卷及文件 ID；秘密文件拒绝硬链接，读取期间持有禁止写入和删除的句柄。
Windows JDK 的 `BasicFileAttributes.fileKey()` 为 null，因此新代码使用 Win32 identity，未放宽为路径字符串或创建时间比较。
写入仅 CREATE_NEW，并使用既有私有 ACL 创建函数；不覆盖、不修复、不清理所有权不确定的失败文件。写后检查身份；中断文件会阻止下次启动。
源对象及 PropertySource 的字符串表示隐藏配置；临时字节数组在提供层用后清零。调用者仍负责其输入字节生命周期，JDBC 所需密码字符串仅在 Java 内存使用。

## 4. 配置加载时序

`main → NativeGate.admit → requireRuntimeArguments → 固定私有文件验证/解密 → Spring initializer → 配置/连接/角色/schema 只读检查 → 条件 DataSource bean → Memory/Conversation/Knowledge Store → Runtime → Storage Status API`。

Windows initializer 在 bean definitions 与 DataSource 条件判断前安装专用非枚举 PropertySource，其优先级高于外部 PostgreSQL 属性。
无本机配置时默认 SQLite 不变；若显式选 PostgreSQL，则拒绝启动；无可信文件却提供外部 PostgreSQL 字段也会拒绝，不能借状态查询连接未受信配置。
配置存在但格式、ACL、密码、连接或 schema 失败时不回退 SQLite；不执行 Flyway 或自动初始化。Finance 默认关闭，提供层不包含任何 Finance 配置键。
非 Windows 启动不安装该 Windows 专用源，沿原配置机制。

## 8. Runtime 不可启动时的诊断与清理

Java 失败诊断只输出 `WORKSPACE_STARTUP_V1` 和固定安全码；缺少可信配置、配置不受信、凭据不可用、连接失败、认证失败、schema 需初始化/不兼容、角色拒绝及 Native admission 拒绝均有代码映射。
连接/认证/schema 映射来自原只读检查的观察结果；没有依据 SQLException 自由文本猜测。其他失败保留 `RUNTIME_START_FAILED`。
Profile Desktop 准入校验失败时显示固定原生说明，不显示路径、异常或凭据。

**当前 WPF 不拥有 Java 子进程，也没有受信的 Java 启动诊断通道；不会读取任意日志或把 stderr 文本当作受信证据。**
Runtime 不响应时显示 `STARTUP_CAUSE_UNAVAILABLE`；健康检查可达但认证未通过时显示 `NATIVE_AUTHENTICATION_UNAVAILABLE`。
因此 WPF 尚不能把未启动、服务不可达、密码错误等原因分别确认给用户；细分原因的完整产品闭环仍 PENDING。
每次重查先清空旧数据库结果；失去可用条件、宿主状态变化、会话/bridge 重建均清除旧观察，旧响应不会重填或继续发 SQL 查询。
