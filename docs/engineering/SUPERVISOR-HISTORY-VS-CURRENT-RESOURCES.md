## 三种资源对象分别判断

### 共享重任务协调锁

准确名称是 `Local\Dot_KAG_Workspace_HeavyRun`。原 `Start-OwnedDesktop.ps1` 只有一次非循环的 WaitOne(0)，在创建 Desktop 前取得；之后仅等待原始 child，finally 尝试释放，没有再获取分支。已用 PowerShell AST 只读确认一处 WaitOne、一处 ReleaseMutex，WaitOne 不在循环内。第一轮重复执行会被已有回执挡在获取锁之前。

脚本的 12 分钟上限只在等待循环得到执行时成立，不能凭源码期限推定旧 PowerShell 已结束；finally 的源码存在也不能代替实际回执。原记录仍缺历史释放方式。

后续实际证据来自独立的新执行调用，不是向旧监督线程发出的重入获取：

| UTC | 已保存事实 |
| --- | --- |
| 16:59:51.1960443 | 新构建监督 PID 49396 在源码明确要求的 Session 1 中取得同名锁，mutexAcquired=true、mutexAbandoned=false |
| 16:59:59.8097072 | 该构建完成并保存自己的锁释放回执 |
| 不晚于 17:09:37.3214434 | 最后一次纯逻辑回归启动 dotnet 前已取得同名锁 |
| 17:09:39.2059928 | 该回归完成并保存自己的锁释放回执 |

Windows 的 `Local\` 是会话命名空间；锁的所有权属于线程，成功等待表示调用线程已取得所有权。[命名空间规则](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)、[Mutex 所有权规则](https://learn.microsoft.com/en-us/dotnet/standard/threading/mutexes)支持以下推论：若旧监督在 Session 1，它不可能一直持锁而同时让后来的独立调用取得该锁；若旧监督在其他 Session，其 Local 对象不阻塞这里的 Session 1 协调锁。原脚本没有重新获取路径，因而不能再把“原调用一直持锁”作为持续阻塞理由。首次记录只直接保存了 child 的 Session 1，不把它伪称为父进程 Session 的独立测量。

mutexAbandoned=false **不能反推旧监督正常释放**：旧对象可能早已失去全部句柄后销毁，或弃用状态已被先前合法获取处理。官方说明[线程结束与弃用处理](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex.releasemutex?view=net-10.0)也不提供历史正常退出证明。

截至本轮没有新的即时占用采样；其他任务以后仍可取得锁。后续动作应在实际执行时按原机制获取并持有锁，不能把 17:09 的回执当作永久通行证，也不能把“未采样现在”直接写成“现在被占用”。

RuntimeProcessJob 是无名称、由 Desktop 持有的 Job，源码设置 KILL_ON_JOB_CLOSE；没有可供本轮打开的固定 Job 名称或存活句柄。原 Runtime 已有真实退出记录，不必为它重建查询入口。此源码不能代替所有历史 WebView 子进程的退出观测；其身份未完整保存，不扩展到全局进程／句柄枚举。

1. 当前父任务明确禁止候选启动，且当前物理内存准入没有有效通过结果。先满足这两项，才有实际运行可讨论；无需为了资源准入先找回无法恢复的历史正常退出码或旧监督 PID。
2. 原脚本 `Round=2` 要求 `desktop-1.json.exited=true` 且 exitCode=0，当前回执不满足，会在获取互斥及启动产品之前停止。这是原两轮正常保存／重开验收的顺序契约，**不是残留锁证据**。不得改写旧回执、伪造 exitCode、删条件或直接重跑来绕过它。
3. 若以后允许使用剩余一次额度，应明确它是新候选的单次诊断启动／正常退出验证，采用独立、可审阅的监督回执，继续累计总数，保留首轮失败。需要正常核对原 b204 Profile、候选 pins、NativeGate、资源及可见退出控制。第一轮没有保存合成资料，所以剩余一次本身不能完成“保存后再独立重开”的双次闭环；不得追加第三次冒充已授权。

这是对未来动作所需范围的说明，本轮没有准备或执行新的启动入口，也没有修改旧监督脚本。正常退出的历史证据缺口继续保留，但不再被混用为永久资源占用门槛。
