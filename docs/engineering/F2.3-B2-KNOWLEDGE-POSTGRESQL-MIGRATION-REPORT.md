## Store 与并发

- 修改原 KnowledgeStore，复用其 admission、revision、jobs、lifecycle 和删除恢复逻辑，增加受控 DataSource 路径。
  只将固定 SQL 中的 Knowledge 表映射到独立名称，不建立第二套业务服务。
- 正常 Runtime 构造路径仍执行 PrivateKnowledgeDirectory 准入、knowledge.lock 和文件校验；
  PostgreSQL 会话排他 advisory lock 阻止不同文件根同时作为同一 Knowledge 的写进程。
- 数据库维护会话使用共享 admission lock，供离线导入后 Store readback 与索引读写；
  它没有文件根，文件发布/删除会明确拒绝，不能作为 Windows 私有 Profile 替代入口。
- 写事务使用 Knowledge 专属事务 advisory lock 与 knowledge_control 行锁，独立于 Memory/Conversation 锁。
  完成和删除的文件阶段持有同一会话级锁，覆盖原有多次 durable transaction 之间的文件窗口。
- 未完成 jobs 的数据库恢复仍标记 INTERRUPTED，不重放作业；实际文件候选清理与删除恢复仍要求合法私有根。
- PostgreSQL 模式拒绝旧的 SQLite restore 发布入口；完整 PostgreSQL 逻辑恢复留给 B3。
- KnowledgeConfiguration 复用 B1 的显式 backend/DataSource；普通用户默认仍为 SQLite，不自动迁移或回退。

## 真值与文件迁移

`SqliteKnowledgeMigration.migrate(sourceRoot, backupRoot, target)` 是显式离线维护入口：

1. 需要停止原 Runtime 并保持停写至后续明确批准的切换；取得原 knowledge.lock 和 SQLite BEGIN IMMEDIATE。
2. 验证源数据库/锁文件及已有私有目录，不修复源权限；备份根必须全新。
3. 使用 SQLite online backup API 备份 knowledge.db，并按真值中的规范 doc-id/revision 路径复制源文件。
   不覆盖旧备份，不导入 lexical.db，不自动删除源或未知 staging 文件。
4. 检查完整性、FK、精确 schema、原始时间、UUID、总量和 jobs/deletes 安全状态。
   PENDING/PARSING 或未完成 deletes 拒绝迁移；READY job 必须对应真实 revision。
5. 核对每个被引用源文件的类型、大小、digest、parser/normalizer、规范化文本、locator、行数和 artifact 大小。
6. 持有只读文件句柄至提交后；Windows 使用真实 NOSHARE_WRITE/NOSHARE_DELETE。
   本机实际观察到 Windows JDK 可不提供 fileKey，新代码不伪造 ID；成功持有该 Windows 句柄时使用句柄及重复摘要核验，其他平台保留实际 fileKey 校验。
7. 目标只要求 Knowledge 真值及 Knowledge receipt 为空，不要求 B1 数据为空，也不删除 B1 receipt。
8. 一个 PostgreSQL 事务内导入四张真值表，逐字段摘要/数量核对、立即验证延迟 FK、建立派生索引，
   再复核源文件，写入 Knowledge 独立 receipt 并提交。
9. 另一连接验证提交和 receipt，再经真实 KnowledgeStore 读取元数据与 preview；最后再次复核源文件。
10. 提交状态未知或提交后校验失败时保留 receipt/文件现场，不自动重试、清表或回写旧 SQLite。

`importSnapshot` 是已隔离 SQLite snapshot/file tree 的数据库导入原语，不授予 Windows 私有文件权限。
文件和 PostgreSQL 不共享原子事务：合法写者由停写、knowledge.lock、数据库 admission/写锁排除；
内容句柄和提交前后复核用于检测变化，不能据此宣称抵御同 SID/admin 的任意目录替换。
**已实际验证 importSnapshot 的合成文件校验、成功导入、晚期索引失败时整事务回滚和另一连接提交后读取。**
完整私有文件 facade 的准入、文件复制中断和恢复仍未验收；合成文件成功不代表 Windows 私有 Profile 发布成功。

## PostgreSQL 派生索引与检索

- PostgreSQL 模式不创建或打开 lexical.db；保留原 LexicalAnalyzer 的 NFKC、小写、CJK 单字/双字和英文词项规则。
- 复用 LexicalChunker、LexicalSnippet 和原文 revision/offset/行号/heading 引用规则。
- 不采用 PostgreSQL 默认语言 FTS。对应用生成的 ASCII token 流实行单 chunk 全词项 AND、4/2/1 字段权重及 BM25 评分，
  再按 document/revision/ordinal 固定排序。
- 使用两次有界流式扫描及最多十条候选堆，复用 chunk/byte 上限和超时；没有承诺高性能索引访问。
- rebuild 在 PostgreSQL 事务中原子替换派生表和版本/语料指纹；读取使用一致性快照并复核指纹，失配拒绝结果。
- 已执行真实 SQLite FTS5 oracle 对照，合成语料上的九个查询通过，覆盖中文、全角/大小写、
  组合重音、标点、AND 边界、排序及引用。该聚焦证据不等同于任意语料完全兼容或性能验收。
