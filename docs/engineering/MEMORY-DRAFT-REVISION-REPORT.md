# 用已审阅草稿修订已有记忆

2026-11-07。基线 `7c76ea71193cc9650715c6868515d36b536f6c13`，分支 `codex/recovery-v3-workspace-core`。本轮交付候选到既有记忆的修订路径，保持 Development-only。

## 选择这一增量的原因

现有链路已有主动候选生成、摘录审阅、编辑、明确保存、版本化存储、字面检索和当前会话的明确连续使用。候选采用后只能成为“新记忆”；虽然已有记录可以手动打开编辑，但无法直接保留新草稿并用它修订既有记录。用户改变偏好时容易另存一条，留下新旧矛盾项。

参考 [Mem0 Update Memory 官方文档的开源用法](https://docs.mem0.ai/core-concepts/memory-operations/update)：先定位既有 memory ID，再用新内容更新，并检查结果。本项目复用已有 `memory.list/get/update`、Native session 授权、Runtime 版本校验和编辑器的未知结果保护；没有引入第二套存储、SDK、模型客户端或自动记忆工具。目标判断仍由用户负责，本轮不实现语义冲突识别。

## 使用路径与结果

对话原文 → 生成／审阅候选 →“采用候选到编辑器”→“用此草稿修订已有记忆”→ 在左侧搜索并选择目标 → 对照旧内容与下方新草稿 →“采用修订到编辑器”→ 必要时继续编辑 →“保存”。手写的新草稿也可使用修订路径；未经采用的候选不会获得写入能力。

选择和采用两个步骤都不写入。最后保存复用原目标的 ID 和精确 revision 更新类型、标题、正文，保留同一条记录；成功后采用 Runtime 返回的版本并刷新列表。普通新建保存路径继续可用。修订不会自动合并旧正文，界面明确说明完整替换及无可恢复旧正文历史；用户须确认准确性。

## 行为与实现边界

- 复用现有分页列表与字面搜索选择一个 ACTIVE 目标，不扫描全库，不自动挑选。进入修订时若当前显示归档列表则切到使用中；期间锁定状态筛选，不会自动恢复归档条目。
- 每次明确选择只读取该条正文，并要求返回 ID、版本和 ACTIVE 状态与点击的列表元数据一致。变更／归档、缺失或读取失败时不能采用，草稿保留；需刷新并重新选择，不用最新版本静默替代。
- 审核中显示旧标题、类型、版本与完整正文；下方新草稿固定，保存按钮禁用，避免误创建新记录。取消目标选择恢复原草稿；采用后进入已有记录编辑状态，仍需 Save，允许用户继续修改。
- 采用到 Save 之间的并发修改由原有 `expectedRevision` 校验处理。冲突、缺失和未知写入结果沿用既有阻断与显式检查流程，不自动重试、退回创建或强制覆盖。连续点击 Save 由原有 action lock 合并为一次写请求。
- 草稿和目标审核仅存于当前页面内存。取消、加载其他草稿、session 重置、页面禁用／离开使目标读取失效；迟到的成功或失败不能恢复审核或替换草稿。已有离页未保存确认与原生 dirty 通知继续生效。
- 生产变更仅 `MemoryPage.tsx` 和两条样式；Native、Runtime、数据库 schema、模型与服务配置均未修改。既有 Native 列表授权限制 get/update 的 ID；Runtime 仍在更新事务中核对版本并递增 revision，本轮只读核对这些源码，未重新执行后端测试。
